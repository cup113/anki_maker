# Document identity is an id, not the title

**Status**: accepted

浏览器里的存档原本以标题为主键（`AL_records_<base64(标题)>`），索引只是一串标题。这带来两个后果：把一份文档改成已有的标题会直接覆盖那一份的记录；把标题改掉则会在 localStorage 里留下一份读不到的死存档。我们改成每份 Document 自带一个 `id`，存档键为 `AL_doc_<id>`，索引记 `[{ id, title }]`，标题退化成可以随时改、也允许重名的属性。

## Considered Options

- **标题为主键，加一次扫描比对来发现改名** —— 改动小，但同标题互相覆盖的问题还在，而且每次保存都要把所有存档读一遍才能知道改的是哪一份。
- **id 为主键，不做迁移** —— 最干净，但已经存了文档的用户会看到文档库变空。

## Consequences

- `migrate()` 在 `init()` 里跑一次：按标题算出稳定的 id（`migrated-<base64(标题)>`），先写新键、再合并索引，最后删旧键。它每次都先尝试导入再清理，不做「索引已存在就跳过」的短路 —— 部署之后仍可能有没刷新的旧标签页按旧格式写存档，那是数据，不是垃圾。
- 旧存档里**已经**因为同名覆盖丢掉的文档找不回来；标题重名在旧数据里意味着它们本来就是同一份。
- 迁移代码会长期留在树里。它只跑一次，但没有它，早期用户的数据就断了。
- 「整份替换当前文档」沿用 id 与 `createdAt`（`model.replace_content`）。换掉 id 就是新开一份，库里会多出一行同名文档，与「替换」的承诺相悖。
- 标题不再唯一，所以改名、导入、打开草稿链接都可能让库里出现两份同名文档。列表只显示到日期（`MM-DD`），同一秒内保存的两份也无法从时间上区分 —— 这是已知的粗糙处，不是没注意到。
- Document 的 `id` 是存档身份，与内容无关：`fingerprint()`（导出缓存的内容判等）不包含它。
